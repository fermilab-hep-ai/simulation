# AIDA-Scout signal production

Signal and control samples for the anomaly-detection search on the CMS Phase-2
L1 scouting stream, generated from `instructions.md` at the repository root.

Everything here is generated by `../make_signal_cards.py`. Edit that script and
re-run it rather than editing individual cards; the per-point `README.md` files
are regenerated too.

```bash
python3 make_signal_cards.py
```

## The generation chain

Two branches, both ending in the same Delphes card and the same PU 200 overlay,
so the two are directly comparable:

```
madgraph:  MG5 hard process ── Pythia8 ── Delphes ── parquet     (existing)
pythia:    Pythia8 hard process ── HepMC ── DelphesHepMC2 ── parquet   (added)
```

`run.sh` picks the branch automatically: a point with a `*_pythia_card.dat` uses
the pythia branch, otherwise the madgraph branch. The pythia branch was added
for this campaign because

* the Hidden Valley, Higgs-portal and Z' hard processes all live natively inside
  Pythia and need no MadGraph step at all, and
* the `jmduarte/mapyde` container ships `DelphesHepMC2/3` but **no
  `DelphesPythia8` binary**, so the README's "path B" recipe cannot run in it.

The driver is `../main_signal.cc`, built the same way `main43.cc` already is. It
applies the CP5 tune block before reading the point's card, so pileup and signal
share a tune. `NEVENTS` / `NSEED` placeholders follow the convention already used
by `minbias` and `upsilon_to_leptons` — which, as a side effect, are now runnable
through `run.sh` as well.

## Requirements from specification section 4, and how they are met

| Requirement | Status |
|---|---|
| No default generator-level cuts | **Met.** The pythia branch applies no phase-space cuts at all (except the deliberate `pTHatMin` in C1). The S5 run card has every pT/dR/mass cut explicitly zeroed. |
| No MLM matching | **Met.** S5 uses `ickkw = 0`, `xqcut = 0`, deviating from the repo's standard cards — see below. |
| PU 200 before PUPPI | **Met.** Both branches go through the existing `PileUpMerger` at `MeanPileUp = 200`. |
| Phase-2 L1 emulation, PUPPI candidates | **Partly.** The Delphes card's L1T view provides `L1TEFlowPuppi` (~6700 candidates/event measured). This is a Delphes approximation, not the CMSSW Phase-2 L1 emulator. |
| L1 menu decision bits per event | **Not done — deliberately deferred.** No menu emulation exists in this repo and none was added. See below. |
| 100k events per point | **Not run.** Cards and infrastructure only, plus small validation runs. |

### Repo convention conflicts, flagged rather than silently followed

The repo's existing run cards ship `ickkw = 1`, `xqcut = 20`, `ptj1min = 10`.
Specification section 4 forbids MLM for these signals and a 10 GeV leading-jet
cut would bias a signal whose jets are 10–30 GeV. The S5 run card therefore
deviates from the repo convention on all three. This is the conflict the
specification asked to have flagged.

## Open items from specification section 6

**1. Is there a SUEP generator integration?** No, and one was not built. The S1
points use Pythia's Hidden Valley module as a stand-in. **They are not SUEP
samples** — a Hidden Valley shower is QCD-like and produces two back-to-back
dark jets, where a real SUEP is a thermal shower that is isotropic by
construction. Isotropy is the entire signature, so the substitution changes the
physics rather than just the label. Each S1 README carries this warning. See
"C4" below for the knock-on consequence.

**2. Does the chain propagate displaced vertices to PUPPI candidates?**
Partially, and **not in the way S3 needs**. Delphes' `ParticlePropagator` does
start particles from their true production vertex and does compute D0/DZ, so the
samples are correct at truth level. But `L1TChargedHadronTrackingEfficiency`,
`L1TElectronTrackingEfficiency` and `L1TMuonTrackingEfficiency` in
`cards/delphes_card.dat` are functions of **`pt` and `eta` only — there is no
|d0| term anywhere**. The S3 evasion mechanism is precisely that L1 tracking is
prompt and loses displaced tracks, so this chain will not reproduce it. S3 is
generated and usable at truth level, but cannot support a "displacement defeats
tkMuon" claim without adding a d0-dependent efficiency or moving to CMSSW.

**3. Which Hidden Valley UFO, and does it match the 4900xxx conventions?**
Moot — **no UFO is used**. The hard process is Pythia's own
`HiddenValley:ffbar2Zv` (particle 4900023, which already has `qv qv~` channels),
so the hard process and the shower are the same code and cannot disagree.

**4. Does the available L1 menu emulation match the PU 200 menu?** There is no
menu emulation in this repo at all — only Delphes L1T objects
(`L1TJetPUPPI`, `L1TScalarHT`, `L1TMuonTight`, `L1TElectron`,
`L1TPuppiMissingET`, `L1TTauTagging*`). Menu bits were deliberately left out of
scope for this pass. They can be computed offline from those branches; each
point's README lists which seeds it should and should not fire.

## C4 — dropped by decision

C4 (anisotropy control: SUEP at fixed multiplicity with the isotropy
deliberately broken) **cannot be built from the Hidden Valley approximation**,
and has been dropped. Under that approximation the nominal S1 points are already
non-isotropic, so "isotropy deliberately broken" is not a knob that exists — C4
collapses onto C1 (the same event, boosted). A genuine C4 needs a thermal shower
whose isotropy can be varied independently of the production kinematics.

The specification calls C4 "the control most likely to change how we interpret
results", so if a thermal SUEP shower is integrated later, C4 is the first thing
to add back.

## Measured behaviour, and one thing to check before trusting S2

From a 50-event validation run at PU 200 on `HVdilep_Zp500_piD2_mumu`:

* L1T PUPPI candidates: ~6700 per event
* Leading L1T PUPPI jet pT: median 123 GeV, 90th pct 213 GeV, max 241 GeV
* HT over PUPPI jets above 30 GeV: median 195 GeV, 90th pct 377 GeV, **max 470 GeV**
* L1T muons: 4.7 per event, median pT 20.7 GeV
* 78% of events have two muons above 2 GeV within |eta| < 1.5 → the BPH
  DoubleTkMuon 2,2 seed fires, as intended for the covered member of the pair

Measured seed fire rates (50 events each, PU 200):

| Seed | ee | mumu |
|---|---|---|
| PuppiHT 450 | 0.04 | 0.04 |
| SinglePuppiJet 230 | 0.04 | 0.02 |
| DoubleTkMuon 2,2 | 0.00 | **0.78** |
| DoubleTkMuon 4,4 | 0.00 | **0.90** |
| DoubleTkElectron 25,12 | **0.58** | 0.00 |
| PuppiETmiss 200 | 0.06 | 0.04 |

### The headline S2 point does not currently work as intended

`DoubleTkElectron 25,12` fires in **58%** of ee events. S2's premise is that soft
di-electrons have nothing below 12 GeV, but at m_Zp = 500 GeV the electrons are
not soft — median reconstructed pT is 27.8 GeV. **As specified, this point does
not demonstrate the gap it was designed to demonstrate.**

The cause is low dark meson multiplicity: ~5–6 decaying mesons share the event,
so each carries ~50 GeV and its leptons ~25 GeV.

**Lambda is not the lever.** Scanning Lambda over 0.5–2 GeV moves the multiplicity
by under 10%, because the specification's own `pTminFSR = 1.1 × Lambda` rule ties
the shower cutoff to Lambda — both move together and the radiation barely changes.

**`HiddenValley:alphaFSR` is the lever.** With `alphaOrder = 0` and
`pTminFSR = 0.5`, at m_Zp = 500 GeV:

| alphaFSR | dark mesons | leptons | median lepton pT | DoubleTkEle 25,12 |
|---|---|---|---|---|
| nominal (`alphaOrder = 1`) | 5.8 | 10.9 | 5.0 GeV | 0.73 |
| 0.5 | 11.3 | 20.8 | 4.0 GeV | 0.69 |
| 0.8 | 14.3 | 25.9 | 3.4 GeV | 0.59 |
| 1.2 | 17.4 | 31.1 | 3.1 GeV | **0.49** |

Even at alphaFSR = 1.2 the rate only halves — the hard tail survives. Lowering
m_Zp is the complementary lever: m_Zp = 200 GeV already gives 0.36 in the nominal
configuration.

**Resolved: m_Z' = 200 with `alphaFSR = 1` was added and measured.** Truth-level,
200 events, ee sample, |eta| < 2.5:

| Point | shower | leptons | dark mesons | median lepton pT | 90th pct | DoubleTkEle 25,12 |
|---|---|---|---|---|---|---|
| Zp500 piD2 | spec default | 10.9 | 5.8 | 5.0 GeV | 41 GeV | 0.73 |
| Zp200 piD2 | spec default | 6.8 | 4.1 | 3.7 GeV | 25 GeV | 0.36 |
| **Zp200 piD2** | **alphaFSR = 1** | **13.9** | **8.5** | **2.8 GeV** | **10.7 GeV** | **0.15** |
| Zp200 piD5 | alphaFSR = 1 | 7.7 | 4.5 | 5.4 GeV | 18 GeV | 0.23 |

The 90th percentile of the electron pT spectrum drops to **10.7 GeV**, i.e. 90%
of the electrons now sit *below* the 12 GeV floor, and the seed rate falls from
0.73 to 0.15. **`HVdilep_Zp200_piD2_ee` / `_mumu` is the pair the headline
result should be built on.** m_piD = 2 is clearly better than 5 for this purpose.

Still to do: confirm at reco level through Delphes at PU 200. The 0.15 above is
truth-level and will shift once L1T electron reconstruction efficiency is folded
in — note that efficiency is markedly worse for electrons than muons in this card
(2.32 vs 4.70 objects per event at Zp500), which is itself a confounder for the
ee/mumu comparison and is documented in the S2 point READMEs.

**Second caveat.** Because every dark meson decays to a lepton pair, the leptons
themselves cluster into PUPPI jets, giving ~120 GeV jets and an HT tail reaching
470 GeV. The hadronic seeds fire at only ~4% today, so this is not the dominant
problem, but re-check it at any new parameter point.

## S5 — what actually gives 8–12 jets

A direct 2-body RPV squark decay gives only 4 jets, so a cascade was added:
`q̃ → q χ̃⁰₁`, `χ̃⁰₁ → qqq`, eight partons at the hard-process level.

**The mass points are forced by physics.** RPV has no invisible particle, so the
entire parent mass becomes visible jets: HT_true = 2 × m_squark. For N jets of
average energy E that fixes 2 × m_squark = N × E. Ten jets at 20–30 GeV therefore
requires **m_squark ≈ 100–150 GeV**. The specification's 300 and 600 GeV cannot
produce 10–30 GeV jets under any topology — at 300 GeV the same cascade gives
eight jets averaging ~75 GeV.

Measured on showered LHE events, anti-kT R = 0.4, |eta| < 2.5:

| Point | N(jet>10) | N(jet>30) | HT₃₀ med | lead jet med | MET | HT450 | events |
|---|---|---|---|---|---|---|---|
| **squark 150 / LSP 100** (run A) | **9.3** | 4.3 | 231 | 68 | 0 | 0.00 | 7 |
| **squark 150 / LSP 100** (run B) | **7.6** | 4.3 | 284 | 99 | 0 | **0.27** | 11 |
| squark 120 / LSP 90 | 7.5 | 3.5 | 356 | 165 | 0 | 0.00 | 4 |
| squark 200 / LSP 150 | — | — | — | — | — | — | 2 |
| squark 300 / LSP 250 | — | — | — | — | — | — | 1 |

**`RPV_squark150_cascade_LSP100` is the recommended point**, but the result is
**not yet solid**. Two independent runs at the same mass point disagree, and both
are fluctuation-dominated at ~10 events.

*Established:* the cascade gives roughly 8 jets above 10 GeV (7.6–9.3, in or next
to the 8–12 band), the leading jet stays well under the 230 GeV seed, and MET is
identically zero. Best of the four points scanned.

*Not established:* whether it clears PuppiHT 450. The two runs give 0.00 and
0.27, and an HT₃₀ median of 231–284 GeV is close enough to 450 that the tail
matters. **Resolve before any sensitivity claim.** If the HT rate is real, drop
m_squark further — HT_true = 2 × m_squark scales directly with it.

### The reported cross sections are NOT usable — read this

MG5 forms a decay-chain cross section as σ_production × Γ_partial / Γ_total, and
the widths here are **supplied by hand** (they have to be, or MG5 cannot build
the propagator — see the blockers below). That makes the reported σ arbitrary.
The symptom is visible directly: the quoted σ is *not monotonic in the squark
mass* — 13.42 pb at m = 150 against 0.0998 pb at m = 120 — which is backwards for
production and is an artifact, not physics.

Normalise instead as **σ_sample = σ(p p → ũ_R ũ_R*) × BR(cascade)**, with
BR ≈ 1 here (only λ''₁₁₂ is on and the LSP sits below the squark, so the cascade
is effectively the only channel). Generate `p p > ur ur~` on its own to get the
production cross section. For reference, inclusive `p p > sq sq~` over all eight
light squark flavours at m = 150 GeV measured **1631 pb**.

The **shapes** above are unaffected by this — jet multiplicity, HT and MET do not
depend on the overall normalisation. But with 1–7 unweighted events per point
they establish the topology only; they are not rate measurements, and the two
heaviest points have too few events to quote at all.

Squarks at 150 GeV are excluded by existing LHC searches. It is kept as a
benchmark — the signature is what matters for AD training — but must not be
presented as a viable model point. `RPV_ewkino{200,300}_UDD` below is the
non-excluded companion carrying a comparable topology.

## S5b — RPV Higgsinos, the non-excluded companion

A near-degenerate Higgsino multiplet (χ̃⁰₁, χ̃⁰₂, χ̃±₁ all ≈ μ) decaying through
λ″₃₂₃ → t s b.

**Why it is not excluded.** Production is *electroweak*, so σ is O(pb) rather
than the ~1600 pb of 150 GeV squarks. The RPV multijet searches that exclude
light squarks are driven by strong production and have very little reach against
EW-produced states. The binding constraint is LEP, m_χ± ≳ 92–103 GeV, so
200–300 GeV is comfortably allowed.

**Why heavy flavour is essential.** A Higgsino couples to a quark and a squark
through *that quark's* Yukawa. With λ″₁₁₂ (u d s) the decay is Yukawa-suppressed
to the point of being non-prompt, so a pure-Higgsino benchmark with light-flavour
decays does not work at all. λ″₃₂₃ goes through the **top** Yukawa, which is
large — the decay is prompt and unsuppressed.

Allowing heavy flavour therefore does two things at once: it makes a genuine
pure-Higgsino benchmark possible, and it raises the jet multiplicity from 6 to
**8–10**, because `χ̃⁰ → t s b` with a hadronic top is five jets rather than
three. Several jets are b-tagged, and MET is small (only from semileptonic tops).

**Mass choice.** The top must be on shell. Below ~180 GeV the t s b mode closes,
the decay goes four-body through an off-shell top, and the Higgsino becomes
**long-lived** — a displaced multijet signature. That is a legitimate and
arguably more interesting signal here (it overlaps with the S3 displacement
theme), but it is a different sample and was not built.

**Measured** (500 showered events each, anti-kT R = 0.4, |eta| < 2.5):

| Point | N(jet>10) | N(jet>30) | HT₃₀ med | lead med | MET med | HT450 | Jet230 | unweighting |
|---|---|---|---|---|---|---|---|---|
| `RPV_ewkino200_UDD` (prompt, t s b) | 7.1 | 4.7 | 355 | 122 | 8 | **0.32** | **0.16** | 530/2000 |
| `RPV_ewkino150_UDD_ctau10mm` (displaced, c s b) | 6.4 | 3.8 | 238 | 89 | 6 | **0.11** | **0.04** | **2000/2000** |

Two corrections to what the arithmetic predicted:

* **Multiplicity is 7.1, not 8–10.** Jets merge and some fall below 10 GeV.
  Neither Higgsino point reaches the 8–12 band; the squark cascade at 150/100
  (9.3) remains the best on that axis.
* **The prompt point leaks into the menu** — 32% fire PuppiHT450 and 16% fire
  SinglePuppiJet230. The hadronic top that buys the multiplicity also supplies
  hard jets, and HT_true = 400 GeV sits too close to the 450 seed. It gets worse
  at 300 GeV, and the mass cannot be lowered without losing the on-shell top.

**The displaced point is the better signal**: below the top threshold there is no
hadronic top, so it fires HT450 in only 11% and Jet230 in 4% — and the same fact
that suppresses the jets is what makes it long-lived. It is also by far the
cheapest S5 point to produce (full 2000-event request unweighted, against 7/1000
for the squark cascade).

## S5c — displaced RPV Higgsino, and the displacement is verified

`RPV_ewkino150_UDD_ctau10mm`: below the top threshold λ″₃₂₃ (t s b) closes, so
this uses λ″₂₂₃ (c s b), which runs off the **charm** Yukawa — smaller by roughly
(y_c/y_t)² ~ 10⁻⁵. The Higgsino is long-lived as a consequence of the mass being
below m_t, not by fiat.

Because the decays are in the matrix element, the daughters would normally be
written at the primary vertex and the displacement lost. Two things prevent that:
`time_of_flight = 0` in the run card makes MG5 write the resonance lifetime
(VTIMUP) into the LHE, and the width is set to hit the target cτ via
cτ[mm] = 1.973×10⁻¹³/Γ[GeV].

**Verified over 4000 resonance entries:** VTIMUP mean **10.02 mm**, median
**6.84 mm** against the expected 10·ln2 = 6.93, max 90.5 mm — a textbook
exponential at the requested lifetime. The mechanism works.

To scan the lifetime, change only the `1000022` width in the customizecards; the
process directory does not need regenerating.

Same downstream caveat as S3: the Delphes L1T tracking efficiencies have **no d0
dependence**, so this chain will not reproduce the loss of displaced tracks at
L1. The sample is correct at truth level.

### Two blockers found along the way

* **MG5 `compute_widths` zeroes any partial width below the QCD scale**
  (~0.2 GeV). The compressed cascade widths are 0.01–0.03 GeV — physically
  prompt, but written out as exactly `0.000000e+00`, leaving the squarks and LSP
  **stable**. A light RPV LSP can never be described with a decay table this way.
* **Letting Pythia recompute the widths** (`SLHA:useDecayTable = off`) fails
  differently — its RPV machinery emits invalid particle codes on this UFO
  (`unknown particle code, id = -2000304`) and every event is rejected.

Putting the cascade in the **matrix element** sidesteps both: the LHE arrives
fully decayed and no decay table is consulted.

### Cost warning

The 8-parton decay chain unweights **very** poorly, and raising the
Breit-Wigner widths did not fix it:

| request | widths (squark / LSP) | unweighted events | efficiency |
|---|---|---|---|
| 1000 | 1e-2 / 1e-6 GeV | 7 | 0.7% |
| 5000 | 1.5 / 0.1 GeV | 11 | 0.2% |

At ~0.2–0.7% a 100k-event production needs O(10⁷) trial events. **This point is
orders of magnitude more expensive per event than anything else in the
campaign**, and that cost, not the physics, is the main obstacle to resolving the
HT450 question above.

If S5 is wanted at scale, the decay chain is the wrong mechanism. The options are
MadSpin (decay the production sample afterwards rather than in the matrix
element), or a spectrum where the widths clear MG5's QCD-scale floor so ordinary
decay tables work again — which means a larger squark/LSP splitting, at the cost
of a harder leading jet.

## Cross sections

Pythia LO, no k-factors applied.

| Point | sigma (pb) |
|---|---|
| `HVdilep_Zp500_piD2_ee` / `_mumu` | 5.236 / 5.585 |
| `HVdilep_Zp500_piD5_ee` / `_mumu` | 5.237 / 4.215 |
| `HVdilep_Zp1000_piD2_ee` / `_mumu` | 0.4168 / 0.3397 |
| `HVdilep_Zp1000_piD5_ee` / `_mumu` | 0.4735 / 0.3879 |
| `HVdilep_Zp500_piD2_mumu_ctau*` | 5.585 (lifetime does not change sigma) |
| `Zprime_qq_m500` | 154.8 |
| gg → phi reference, m = 125 / 400 | 28.07 / 5.212 |
| gg → phi + j reference, pTHat > 150 | 1.945 |

The ee and mumu members of a pair differ by a few percent purely from Monte
Carlo statistics on short runs; they share a hard process and should be
identical in the limit of large statistics.

**Normalisation warning for all Higgs-portal points (S1, C1, S4).** The sigma
printed by the generator is sigma(gg→phi) multiplied by Pythia's internal
open-channel fraction. For an *added* exotic channel that fraction is a
width-bookkeeping artifact rather than a physical branching ratio — it comes out
around 1.4e-4 at m_phi = 400. Normalise these samples yourself as
sigma(gg→phi) × BR, using the reference sigma above and your own assumed BR.

```bash
simdir=/afs/cern.ch/work/o/oamram/public/collide_simulation

  /cvmfs/unpacked.cern.ch/registry.hub.docker.com/jmduarte/mapyde:latest \
```
